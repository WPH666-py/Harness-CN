# Agent Note: 运行日志窗口会报告始终没有应答的快照读取

Status: implemented

[English](2026-10-13-log-window-snapshot-deadline.md) | 中文

## Problem

`log-viewer.js` 只有在快照读取落定之后，才写入列表行、状态行与「暂无记录」行。在此之前，页面上唯一
的文字是本地化标签。因此，一个既不 resolve 也不 reject 的读取会留下一个只显示工具栏的窗口——与
「这次运行什么都没记」是同一幅画面，而这恰恰是那个窗口存在的意义所在。

用户针对 0.1.5-rc.21 报告的正是这种情况：窗口有本地化标签，没有列表行、没有状态行、没有「暂无记录」
行，也没有失败提示，而 `harness.log` 里就有这次运行的行。同一个页面由全新的 Chromium 客户端对同一个
外壳加载时，能渲染出保留的行及其状态行，可见页面、外壳 API 与 fetch 路径都正常；用户看到的窗口正是
读取始终没有落定时会产生的状态。

`log-viewer-boot.js` 覆盖不了这种情况。它在模块一启动就停止等待，而模块在读取任何内容之前就设置了页面
标题，因此「启动了随后卡住」正是该守卫判定为成功的状态。

## Decision

`readSnapshot()` 通过截止时间读取快照，并重试。每次尝试让 `getLogs()` 与
`SNAPSHOT_TIMEOUT_MS`（5000 毫秒）竞速；失败或超时的尝试会被重试，最多 `SNAPSHOT_ATTEMPTS`
（4）次尝试，间隔为 `SNAPSHOT_RETRY_DELAY_MS`（500 毫秒）乘以尝试序号。重试期间页面显示一条失败提示，
写明当前是第几次尝试以及失败原因。读取最终成功时，`main()` 在列表渲染之后撤下该提示；当所有尝试都
失败时，最后一次失败传播到既有的 `main().catch`，由它报告。

提示存放于带键的映射（`bootNotices`）而不是单次元素写入，因此撤下一条已恢复的重试提示不会抹掉与之
无关的失败，例如实时日志流不可用。`reportBootFailure(text, key)` 对上述调用方保持原有单参数行为。

## Alternatives considered

**让 `log-viewer-boot.js` 报告卡住。** 该守卫在模块启动时就停止等待，而模块在读取之前就设置了标题。
要在那里覆盖本情况，就得把启动信号移到首次渲染之后，那样又会把快照读取的卡住报告成模块从未运行。

**把截止时间放进 `shell-api.js` 的 `request()`。** 每个外壳窗口共用那个辅助函数；别处的慢端点并不是这个
窗口该报告的失败，而运行日志窗口正是「沉默与空运行无法区分」的那个界面。

**用进度指示代替提示。** 进度指示是同样的沉默，只是加了动效。读取的 rejection 携带用户需要的信息，
因此窗口把它显示出来。

## Consequences

窗口如今总是落在三种可见状态之一：列表行、写明日志文件的「暂无记录」行，或一条失败提示。外壳卡住时，
最多付出四次尝试的代价（按当前取值约 23 秒）之后给出最终提示；而短暂卡顿一旦消退，重试就会立即渲染。

该窗口的客户端模块为每次尝试增加一个定时器。外壳其他部分不变：服务端端点、环形缓冲与实时流保持原有
行为。

`node --check` 可解析改动后的模块。本仓库的覆盖体系没有加载外壳 `rsc/` 客户端模块的通道，因此该页面在
真实 Chromium 引擎中通过 DevTools 协议对运行中的外壳进行验证：保留的行与状态行会渲染；而在日志端点被
一直挂起时，窗口显示重试提示，而不是保持空白。
