# Agent Note：登录等待态还留着「登录」按钮，运行日志窗口会开成空白

Status: implemented

[English](2026-10-17-account-panel-and-run-log-polish.md) | 中文

## Problem（问题）

两处 rc.29 桌面载荷上的发布后修正，都是对着已安装的应用报出来的。

**账号面板。** 浏览器登录流程启动之后，设置 → 账号与余额 渲染出「请在浏览器中继续」和一行 `[登录] [取消] [打开浏览器]`：开始登录的控件和结束这次登录的控件并排摆着，而第二次「开始」只会替换掉浏览器正握着的这次尝试。

**运行日志。** 运行日志打开后，窗口里该有的标签都在，列表是空的，既没有状态行也没有错误提示。同一时刻从主窗口探测 `/shell-api/logs`，控制面返回 207 条 —— 数据在，只是页面从来没显示出来。

## Cause（原因）

**账号面板。** `AccountSection.tsx` 在未登录分支无条件渲染「登录」，只用 `ACTIVE_PHASES` 过滤了取消控件。「登录」的 `disabled` 来自 `state.busy`，而 `startSignIn` 应答之后、浏览器回调之前 `busy` 是 false，于是面板看起来随时可以再开始一次，尽管这次尝试还在跑。

**运行日志。** `apps/desktop-shell/rsc/log-viewer.js` 的 `main()` 先接上实时流（`subscribeEvents`，一条长连接的 SSE 请求），再去读快照。两者打的是同一个回环地址，Chromium 对一个源允许六条连接；应用自己的页面占着几条长连接，内置插件窗口还占一条。流一旦占掉最后一个名额，快照请求就排在它后面，页面停在 `await readSnapshot()` 上，屏幕上什么都没有。窗口自己的注释早从另一面描述过这个失效方式：「没有截止时间时，标签出现了、列表空着，窗口会声称这次运行什么都没记。」

## Evidence（证据）

- 已安装的应用，经 WebView2 调试端口驱动：点「登录」后进入「请在浏览器中继续」，改动后 `buttons: [取消]`、`hasSignIn: false`；点取消回到空闲面板，「登录」控件回来，且没有进行中的尝试。
- 在运行中的应用里用 iframe 复现查看器页面，渲染出 `显示 1 条，内存保留 1 条，已丢弃 0 条。` 和一行记录 ⇒ 页面自身逻辑没问题，失败在请求顺序，不在快照。
- 调整顺序后，新开的窗口渲染出 `显示 65 条，内存保留 65 条，已丢弃 0 条。  C:\Users\admin\AppData\Local\com.harnesscn.desktop\logs\harness.log` 与 65 行。
- `readSnapshot()` 本来就带重试（`SNAPSHOT_ATTEMPTS = 4`、`SNAPSHOT_TIMEOUT_MS = 5000`）并把每次失败写在列表上方 —— 这正是被排队的读会让窗口空白五秒、之后才开始解释自己的原因。

## Decision（决定）

- 未登录分支只在没有进行中尝试时（`attempt === null || !ACTIVE_PHASES.includes(attempt.phase)`）渲染「登录」；有尝试时渲染取消控件与授权链接。这一行改为可换行而不是溢出，链接加了点水平内边距，和按钮对齐。
- `log-viewer.js` 先读快照，再挂实时流。`merge()` 本来就按序号丢弃快照已带过的条目，所以后挂不会漏。

## Alternatives considered（备选方案）

**只在窗口可见时挂流。** 流正是让列表在窗口打开期间保持最新的东西，而可见性随时会变；调整顺序消除了依赖，又不必让流变成条件挂载。

**把 `SNAPSHOT_TIMEOUT_MS` 调大。** 那只会把五秒的空白窗口变成更长的空白窗口 —— 问题在排队，不在截止时间。

**去掉实时流改成轮询。** 正确但更重：窗口存活期间是一请求一轮询，而不是一条连接；而快照路径本来就该是那个不许等的部分。

## Consequences（后果）

首个请求是快照的窗口一定能画出来，不管别的窗口占着多少条长连接；实时流挂上之后新行照常到达。账号面板不再同时提供两条互相矛盾的控件，两处都有用例钉住：相位矩阵现在断言每个进行中相位都没有「开始」控件，手势用例先在空闲面板点「登录」，再看等待态换成取消与打开浏览器。
