# Agent Note: The desktop signs in to a DeepSeek account and grants its bonus credits

Status: implemented

English | [中文](2026-10-16-desktop-deepseek-account-and-bonus-credits.zh.md)

## Problem

Harness-CN's desktop distribution had no account surface: a user could not sign in with a DeepSeek account, could not see the balance that account carries, and could not collect the bonus credits (赠金) the platform grants. The upstream account packages on npm carry exactly that surface, so the question was never whether to write a platform client — it was which upstream release can run on this line and which half of it can render here.

The release that carries the bonus reads and acknowledgements is `0.1.7-rc.2`: `getUnnotifiedBonuses` and `ackBonusNotified` appear in no earlier package (`0.1.7-alpha.1`, `alpha.2`, and `rc.1` all lack them). Three obstacles stood between that release and this line, and each was verified rather than assumed:

- Its generated typert manifests describe codec schemas with a `create()` factory, which this line's loader rejected with `parameter codec is not backed by a zod v4 schema`, failing the whole plugin tree. [Fixed separately](../architecture/2026-10-16-typert-codec-schema-forms.md).
- Its peers are declared at `^0.1.7-alpha.1` (`dsh-authorization`, `dsh-credentials`, `dsh-host-webserver`, its own base package, `dsh-typert-protocol`) while the profile carries `0.1.5-rc.26`. The profile workspace sets `autoInstallPeers: false`, so pnpm warns instead of installing a second copy of the seams, and the APIs the packages call are the ones the line already has.
- Its **browser half cannot be shipped here at all**. The upstream Client registers its rows into `settings.launcher`, `settings.models.sign-in`, and `shell.quota-notice`; this line's Client has `settings.section` and `shell.overlay` and no others, so the package mounts and renders no entry. The `0.1.7-rc.2` build additionally injects a `configForms` service this line does not have, and gates its whole apply on `"dshDesktop" in globalThis`.

## Decision

The host half comes from upstream; the browser half is ours.

**Host.** `@deepseek-ai/dsh-deepseek-account-platform` and `@deepseek-ai/dsh-api-account-controller` `0.1.7-rc.2` enter the desktop seed as bundled plugins with `active: false`, and `@deepseek-ai/dsh-deepseek-account` `0.1.7-rc.2` is declared as their runtime dependency (it is a peer, so pnpm never installs it on their behalf). Four rows mount them — `authorization`, `deepseek-account` (with `desktopPlatform` derived from `process.platform`), `account-controller`, and our Client package — from `apps/desktop-host/config/desktop.cordis.patch.yml`. That layer is the only one that can name them: these packages are installed only by the desktop seed, while the shared bundle patches are loaded by every profile, where an insert naming an absent package fails the whole tree. The rows are not listed in `dsh.profile.bundles` because none of the packages declares a `dsh.bundle.patch`, which `inspectPlugin` requires of a listed bundle.

**Browser.** `packages/client/ui-settings-account-harness` mounts the generated Remote contribution itself — `import accountRemote from '@deepseek-ai/dsh-api-account-controller/remote'`, then `await ctx.remote.$mount(accountRemote)` as the first statement of its `apply`, registered as the first effect so Cordis unwinds the namespace after the stream and the row that read it — and registers exactly one `settings.section` row (`id: 'account'`, `order: -10`). It injects `['slots', 'locale', 'remote']` rather than `remote.account`: this line's Client assembly (`packages/api/remotes/src/client/index.ts`) mounts fifteen fixed contributions and account is not one of them, so waiting on the name would wait forever, and the wait would be a self-reference anyway — this `apply` is what provides it. Mounting a namespace the Host does not serve cannot fail the boot, because `validateContribution` checks the contribution's own descriptors and the namespaces already mounted and never the Host's face, so an absent account stack surfaces as a failed read that the row renders. The plugin therefore declares no product gate of its own, where the upstream Client gates its apply on `"dshDesktop" in globalThis` instead, which this line's shipping Windows carrier — the Tauri shell — does not expose, so the row would have stayed unrendered in the product it was written for. The row is the interface: it carries no heading, description, or other standing copy, and prints a status line only while a sign-in attempt reports a phase (`initializing`, `waiting-browser`, `exchanging`, `committing`, `expired`). Signed out, the section offers sign-in (`startSignIn(client, window.location.origin, 'desktop')`) and, while a phase is active, a cancel. Signed in, it shows the balance as two rows — 充值余额 and 赠金余额 — with the platform links the account state carries (`usageUrl`, `topUpUrl`) and a sign-out that first calls `hasRunningAccountTasks()`. A link out of the product is opened by the carrier rather than followed in place, and the two carriers differ. The shipping Tauri shell answers a page's new-window request by handing the address to the platform browser (`on_new_window` → `open_in_browser`, which passes on only `http`/`https` and refuses loopback, so an `<a target="_blank">` is not a way to navigate the shell itself), which is how the two platform links reach the user and how an attempt's `authorizeUrl` is opened: the account service produces that URL and opens nothing itself, so the row opens it once in a new window when the attempt reaches `waiting-browser` — keyed on the attempt id, because the state stream re-publishes every frame — and keeps an `open` link beside the status line for the Electron shell, where the automatic request is denied too. The Electron shell this repository develops against denies that request (`setWindowOpenHandler` returns `deny`, and `will-navigate` allows only `dsh-app:`), so those links are inert there and only there.

**Bonus credits.** A notice is read once when the account enters the signed-in state and once when the section mounts, never on a timer. The first unnotified credit is rendered as a non-modal card whose text is the server's own `message`, verbatim; a notice whose `expiresAt` has passed is dropped unread. Showing it queues exactly one acknowledgement per order (`ackBonusNotified(accountId, orderId, client)`), retried while the section stays mounted with a delay that doubles from 1000 ms to a 60 000 ms cap, and a successful acknowledgement refreshes the balance, because the platform's answer can change what the account holds. Every subscription the section needs lives in the plugin's injected hooks, so unmounting the section cancels its stream and its retries.

The client passes the metadata the platform requires on each call — client version, active locale, UTC offset — and the packages derive the request headers from it (`x-client-platform` is `desktop-win`/`desktop-mac` under the desktop host). The protocol, the PKCE flow, the endpoint URLs (`/api/v0/users/get_unnotified_bonuses`, `/api/v0/users/ack_bonus_notified`, `/auth-api/v0/users/current`, `/api/v0/users/get_user_summary`, `/auth-api/v0/users/logout`), and the session-expiry rule stay owned by the upstream packages; this product does not re-implement them.

## Alternatives considered

- Ship upstream's Client package (`@deepseek-ai/dsh-client-ui-settings-account`) and let it render. It cannot: every slot it registers into is absent from this line, which is a property of the slot registry, not a configuration.
- Patch upstream's Client bundle the way the repository patches third-party packages (`dsh-wechat`, `dsh-rule-engine`). Removing `"configForms"` from its inject list and guarding the onboarding block makes the package load, but the entries still have no slot to render into, and the patch would have to be re-verified against every upstream release.
- Stay on `0.1.7-alpha.1`, whose host packages already load here. Rejected: the bonus reads and acknowledgements do not exist in that release, and granting credits after sign-in is the feature.
- Put the section in an existing first-party Client package such as `ui-settings`. The surface needs a host package only the desktop seed installs, so every other profile would carry dead code, and the Client coverage gate would cover code no other profile can execute.
- Read unnotified credits on a timer, or acknowledge before rendering. Both were rejected for the same reason the upstream behaviour is shaped this way: the acknowledgement is a fact about what the user was shown, and a polled read can surface the same credit twice or acknowledge a card that never painted.

## Consequences

The account stack was verified by booting the real profile rather than by inspection. A probe that injects both services reports the shipping path ready at 15.4 s with `getState`, `getBalance`, `startSignIn`, `getUnnotifiedBonuses`, and `ackBonusNotified` all present; the identical configuration failed at 16.1 s before the codec change. `getState()` on a signed-out profile returns `{"status":"signed-out","attempt":null,"links":{"usageUrl":"https://platform.deepseek.com/usage","topUpUrl":"https://platform.deepseek.com/top_up"}}` and `getProfile()` returns null, which is what the signed-out section renders from.

The seed grows by three npm packages and the profile by their files; the account surface costs every installation that much, whether or not the user signs in. The bonus card's acknowledgement is best-effort: a failed one is retried while the section is mounted, and a user who closes the section before it succeeds keeps the credit unnotified, which is the safe direction.

Sign-in against the real platform, and a real granted credit, were not exercised here — the packages' own client code reaches the platform, and what this note verified is that they mount, expose their Remote surface, and boot to ready on this line.
