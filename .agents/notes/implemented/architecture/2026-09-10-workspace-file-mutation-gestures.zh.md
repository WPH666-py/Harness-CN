# Agent Note: Workspace file mutation gestures

Status: implemented

[English](2026-09-10-workspace-file-mutation-gestures.md) | 中文

## Problem

Host 已经能修改工作区文件：[Workspace file mutations](2026-09-10-workspace-file-mutations.zh.md) 交付了五个限定在工作区内的 verb，用于新建目录或空文件、删除条目、复制子树、移动或重命名条目。`files` tab 一个都用不上。它是为读取而建的：store 只保存一个 tab 的目录列表状态（`root`、`levels`、`expanded`），face 只有三个列目录的方法，唯一的控件是重新读取。[Sidebar text preview and file tree](../feature/2026-09-05-sidebar-text-preview-and-file-tree.zh.md) 说明了这棵树为什么是一个不认领地址的页类型、为什么自带按层级的目录列表 store，并把文件管理器其余的手势留在 Deferred 里。

把两者接起来，引出了这两份记录都没有回答的问题。读者手上的状态——选中的行、为粘贴而握住的条目、打开中的名称输入框、上次手势失败的原因——该住在哪里，考虑到 tab 的正文会随 tab 切换而卸载，而树的目录列表状态又已经住在一个按 tab 分桶的 store 里？当选中的是文件而不是目录时，手势作用在什么上？一次修改落地之后，Client 是把它已知的条目补进缓存的那一层，还是让 Host 重新列出该层？读者如何得知 Host 拒绝了，以及谁确认一次无法撤销的删除？还有，Session 到底怎么到达这棵树——树只是右列众多 tab 中的一个页类型，而右列自己的展开状态属于另一个包。

## Decision

`packages/client/ui-sidebar-files` 在它已经画出的那棵树上补齐了文件管理器的手势：一条工具栏、行选择、右键菜单、行内名称输入框、删除确认，以及一个打开这棵树的 Session 头部控件。它们经由该包既有的 store 和 face 执行，五个修改类 verb 通过 `workspaceFiles` Remote 命名空间到达 Host。

### 读者的工作状态住在 tab 的分桶里

`FilesTabState` 在目录列表状态之外新增四个成员：`selected`，某一行的绝对路径或 `null`；`clipboard`，一个 `FilesClipboard`（`{ mode: 'copy' | 'cut'; path }`）或 `null`；`draft`，一个 `NewEntryDraft`（`{ parent; kind: 'file' | 'directory' }`），指名那个仍在等待名称的新条目，或 `null`；以及 `notice`，上次手势结算时的 `RemoteFailure`，或 `null`。`start` 把四者都播种为空，`selected`、`clipboarded`、`drafted`、`noticed` 和 `pruned` 写入它们。

它们住在 store 而不是正文的局部状态里，因为它们比正文活得久。tab 的正文随 tab 切换而挂载和卸载，而读者在一次访问中握起的条目，要在下一次访问里粘贴；名称输入框也必须活过它被打开时正经历的那次切换。有两个事实恰恰因为不能活过正文而留在组件状态里：打开中的右键菜单（`menu`，携带它作用的行与当时指针的位置）和等待确认的删除（`removing`）。两者各自都是随正文关闭的浮层，而一次切换之后再恢复的菜单会被锚定在一个已经不再有任何意义的指针位置上。

`selected` 同时清除 `notice`：选中另一行意味着读者已经往前走，于是关于他留下的那次手势的那一行不再显示。

### 手势作用在选中行的目录上，否则作用在根上

`destinationOf(state)` 回答头部的新建与粘贴控件落在哪里：选中行是目录时就是它，选择是文件、`other` 条目，或什么都没有时就是树的根。它从该行所在的那一层读出选择，因此当选择所在的层已不再被列出，或该层已不再持有这个条目时，回退到根，而不是指名一个树看不见的目录。

右键菜单携带被问到的那一行，而不是去读选择，并且只在目录上提供粘贴，因为只有目录里有东西可粘。`open` 执行该行自身点击所执行的动作：目录切换展开，文件经 owner 的 `tabActions` 打开。新建把行内输入框画在目标目录之下，并在该目录处于折叠状态时先展开它，因为折叠的目录不画任何一行，输入框没有可落脚之处。头部的粘贴控件在工具栏里保留自己的位置，并在剪贴板为空时禁用，于是这一排控件的宽度不会随着读者复制粘贴而变化。

### 落地的修改会重新列出它改动的那一层

`createEntry` 重新列出它新建所在的目录。`removeEntry` 忘掉被删除的路径，并重新列出容纳它的那个目录。`pasteEntry` 重新列出目标目录，而落地的 `cut` 还会重新列出条目离开的那个目录，除非那个目录就是目标目录。每一次重新列出都走 face 的 `load`，它会作废该层仍在飞行中的那次列出，因此一次刷新和读者自己的展开手势不会同时写入同一层。

之所以重新列出而不是就地打补丁，是因为这份目录列表是树所画一切的唯一权威：每个条目的 `type`、该层的截断标志，以及由树重新排序的端点顺序。补进去的一行必须把这三者全部复现，而粘贴这一情形说明树做不到：`FilesClipboard` 只记下模式和路径，`copy` 与 `move` 只回答产出条目的 `absolutePath`、`version`、`bytes` 和工作区路径——从不是它的 `type`——因此一次粘贴落地之后，Client 仍不知道它放下的那个条目是目录、文件，还是别的什么。也没有任何东西在监视文件系统，所以这次重新列出同样是某一层得知磁盘上还有别的什么变化的唯一途径。

`pruned` 忘掉被删除路径的那一层、它之下的每一层、曾指向它们的那几条展开路径，以及落在被删子树之内的选择。之后的条目可能复用这个路径，它不能画出被删子树的目录列表，也不能继承一个指向已消失之物的手势。

### 复制保留剪贴板，剪切释放它

一次粘贴把自己的目标拼成目标目录加上源的 basename（`childPath(destination, baseName(clipboard.path))`），`copy` 模式的剪贴板调用 `copy`，`cut` 模式的调用 `move`。落地的 `cut` 清空剪贴板；落地的 `copy` 保留它；两种模式下一次被拒绝的粘贴也都保留它。

剪切的源已经从剪贴板所指名的路径上消失，所以第二次粘贴会让 Host 去移动一个不复存在的路径：剪贴板将握着一个只会失败的手势。复制把它的源留在原地，因此一次握起就能把条目放进读者粘贴到的任意多个目录，而这正是复制它所要求的结果。被拒绝后仍保留剪贴板是同一个道理的另一面：读者换一个目标，而不是把条目重新握起一次。

粘贴保留条目自己的名称，因为这个手势是放下一个条目，不是命名一个新条目。这次变更不交付重命名，而一次索要名称的粘贴就是披着粘贴外衣的重命名。Host 会拒绝已被占用的目标，因此名称已被占用时的粘贴——包括把一个剪切条目粘回它来自的那个目录——以 `workspace-file/exists` 失败并如实说明，而不是覆盖或合并。

### 被拒绝的手势在树上方如实说明

`gestureLine` 把本包需要分支的三种拒绝映射为关于该手势的文案：`workspace-file/exists`，目标处已有同名条目，因此没有覆盖任何东西；`workspace-file/not-empty`，该目录里还有内容，因此没有被删除；以及 `workspace-file/not-found`，条目已经不在了，因此可能被移动或删除过。其他任何失败都显示它自己的 `message`，因为传输层错误或未分类的 Host 错误码让这棵树没有什么有用的话可以补充。这一行位于头部之下、树的滚动容器之上，因此无论读者读到哪里它都在。选中另一行会去掉它。

名称输入框会一直打开到新建落地为止，因此被拒绝的名称把读者已输入的文本留在说明原因的那一行旁边。空名称从不发送：在空输入框上按 Enter 会为一段读者从未打算输入的路径段发起一次往返。按 Escape，或输入框失去焦点，都会关闭它而不向 Host 索取任何东西。

### 删除在面板内确认

从右键菜单发起的删除会打开一个 `Modal`，指名那个条目——目录时加上“及其全部内容”——并且只在读者确认后调用 `removeEntry`。取消，或关闭该模态框，都不调用任何东西。文件以 `recursive: false` 删除，目录以 `recursive: true` 删除，因此决定该选项的是条目自身的种类，而不是读者的措辞。

这个确认属于面板，而不属于 Host。`remove` 是 `ctx.workspaceFiles` 上五个修改类 verb 之一，其调用方包含非交互的调用方；一个在每次删除前都要询问的 Host，会让它们每一个都去等一个可能并不存在的读者。面板也是唯一知道哪一次点击才算决定的地方——打开菜单的那次右键不算——并且只有在那里才能用读者自己的语言指名该条目。

### 五个 verb 由生成的 client 推导而来

`WorkspaceFilesMutations` 是 `Pick<ClientRemote['workspaceFiles'], 'createDirectory' | 'createFile' | 'remove' | 'copy' | 'move'>`，而绑定后的 face 是这个类型加上树自己收窄过的 `list`。这些 verb 只被声明一次，由 Host 生成的 client 声明，因此 Host 的某个 verb 增加、去掉或重排一个参数时，在本包是编译错误，而不是一次传错参数的调用。在这里手写一个结构化类型，会对着过时的参数列表通过编译，然后在线路上失败。

每个修改类 verb 转发自己的调用，而不是捕获那个方法，因此一个重新挂载的 `workspaceFiles` 命名空间会在下一次手势时把活的方法交给这棵树。只有 `list` 做了收窄，因为树保留 entries 和截断标志，丢弃端点的工作区相对路径。每个修改类 verb 在记录的 `signal` 已经中止时直接返回而不发起调用，而在该中止之后结算的结果不写入任何东西。

### Session 头部控件是无状态的

本包多注册一项：`conversation.session.header.utilities` 下 id 为 `workspace-files`，画 `FilesToggleAction`，一个文件夹图标，其无障碍名称取自该命名空间的 `toggle.label`。这个坑位是按 id 寻址的 list cell，因此调用方可以精确替换这一个控件而不打扰它的邻居。

该组件不持有任何状态。inject face 闭包持有 `ctx.sidebarRight`，在手势发生的那一刻问右列它是否处于展开状态、以及当前 tab 是否为 `files` kind：两者都成立时用 `toggleExpanded()` 收起右列，否则用 `openTab('files')` 打开这棵树。答案之所以不被存下来，是因为右列的状态不是本包可以读的。`sidebarRight` 声明自己的 store，本包声明树的 store，而组件的数据来自注册项推导的 props（`PropsRuntime`、`PropsRenderSlots`、`PropsStore` 与 inject face），不是来自另一个包的 store。在手势发生的那一刻询问，也是唯一在那一刻为真的答案，因为右列的展开与收起经由本包从来看不到的控件发生。`openTab` 在同一步里显示右列，因此折叠的右列不需要第二次调用。`sidebarRight` 加入本包的 `inject` 列表。

### 新增文案由 locale 持有

这些手势把自己的字符串加进 `sidebarFiles` 命名空间：工具栏的三个标签、五行菜单、两个名称输入框标签、确认框的标题、句子、动作与取消、控件的标签、三行手势拒绝文案，以及树无法分类的失败那一行。`zh` 是键集合的权威来源，`en` 是 `satisfies Record<SidebarFilesKey, string>`，因此英文词典缺少某个键就无法编译。

## Alternatives considered

**把读者的工作状态留在正文的局部状态里。** 剪贴板、选择和名称输入框就会被声明在画它们的地方，store 的成员也更少。否决：正文并不是一个跨访问存在的事实的 owner——它随 tab 切换而卸载，于是读者看一眼别的 tab 就会丢掉手里握着的条目，名称输入框也会在他脚下关闭。store 是这次注册声明的写入集合，而共享的手势事实属于它。

**用修改产出的条目给缓存的那一层打补丁。** 新建或粘贴可以不经往返就插入一行，每次手势省一次请求。否决：树将不得不凭空造出目录列表所携带的事实——粘贴的结果给出路径和版本，却不给条目的 `type`，该层的截断标志也只能靠猜，而端点的顺序本来也不是这一行摆放的位置。之后的第一次列出就会与画出来的内容矛盾：这里叫这个名字的可能是目录，那里却是文件。

**落地的复制也清空剪贴板，与剪切对称。** 否决：这是一种以能力为代价的对称。复制的源还在，因此两种模式并不是同一个手势，而把条目复制后要放进两个目录的读者就得复制两次。这种不对称正是重点，它就写在声明这些模式的地方。

**让粘贴向读者索要目标名称。** 否决：这个手势放下的条目是读者已经握在手里的，而常见情形是把它以自己的名称放进另一个目录；一次名称提示会把单个手势变成一段对话，而且会是打着粘贴旗号引入的重命名。`move` 是未来重命名会用的 verb，今天只能经由一次粘贴到达。

**由 Host 在 `remove` 执行前确认删除。** 否决：`remove` 是一个普通的工作区 verb，与没有读者可问的调用方共享，而把交互步骤放进去，要么让它们阻塞，要么需要一个按调用方的标志，把一份契约变成两份。确认属于面板，因为只有在面板里，破坏性意图才与打开菜单的那次点击区分得开。

**给 `FilesToggleAction` 一个 store，或从 `sidebarRight` 的 store 里读右列的展开状态。** 知道右列状态的控件就能把自己画成按下态或换一个图标。否决：右列的 store 属于 `ui-sidebar-right`，本包的注册只声明树的状态，别无其他；而组件的数据经注册项推导的 props 到达，不是来自第二个 store。服务在手势发生的那一刻作答，而那一刻正是这个切换的答案唯一被用到的时刻。

**只经由它已经注册的引导页入口到达这棵树。** `files` 类型已经是引导页上的一枚胶囊，这个控件等于加了第二条通路。否决：引导页是读者必须先打开的一页，于是这棵树离每个 Session 都有两个手势远，而右列还得长期持有一个唯一职责就是把自己的 tab 交出去的页。头部控件让这棵树离它所属的 Session 只有一个手势。

## Consequences

树的 face 和 store 现在属于一个文件管理器，而不属于一份目录列表：一次修改加它的刷新是两次请求，而改动两个目录的手势（剪切）发起一个 verb 加两次列出。新建十个文件的读者会发起十次新建和十次列出；没有任何东西把它们合并。

刷新不是实时的。没有任何一层在监视文件系统，因此某一层显示的是它上次列出的内容加上读者自己的手势刷新过的部分；由 agent、另一个读者或产品之外做出的改动，要等到重新读取或该层下一次被打开才出现。

粘贴不能重命名，也不能把一个条目放在已有同名条目旁边。拒绝是 `workspace-file/exists`，因此读者必须先删除或移走占用者；而把一个剪切条目粘回它来自的目录会以同样方式失败——一个读起来像空操作的手势被如实报为拒绝。

被拒绝的手势让树保持原样：没有任何层被重新列出，没有任何东西被忘掉，剪贴板被保留，因此读者可以换一个目标重试，而不必重新握起条目。说明原因的那一行是它留下的唯一痕迹，而选中另一行会清除它。

读者的工作状态按 tab 存在，随 tab 消失。页面重新加载不保留任何东西，右键菜单与确认框随打开它们的正文一同消失。

Session 头部控件命名的是 `files` kind 而不是某个实现，因此当产品的扩展接管了该 kind 时，同一个按钮给出的是替换后的页；这个控件是通往这棵树的路，不是通往 `ui-sidebar-files` 组件的路。

## Testing

`tests/store.client.spec.ts` 覆盖新的写入集合：一次只有一个选择及其清除、一个剪贴板条目及其释放、draft、notice 及其被选择清除，以及 `pruned` 忘掉一个子树的层级、展开与选择。`tests/face.client.spec.ts` 覆盖每个手势到达哪里、一次结算写入什么：`createEntry` 经 `createFile` 或 `createDirectory` 带上父目录与名称；输入框一直打开到新建落地，被拒绝时不重新打开任何东西；`removeEntry` 带条目自身的 `recursive`；两种粘贴模式在拼好的目标上分别经 `copy` 或 `move`；一次剪切刷新两个目录，而落在它来自之处时只刷新一个；剪贴板被剪切释放、被复制或被拒绝保留；`pruned` 对被删子树；以及对于 `signal` 已经中止的记录完全不发起修改请求。`tests/files-body.client.spec.tsx` 覆盖画出来的行为：选择标记及它在一次重新列出后的存续、行内输入框的新建/取消/空名称/被拒名称四条路径、工具栏与菜单两条粘贴路径、菜单按种类给出各行、确认框只在确认时调用 Host 而取消不付代价、各条拒绝文案、`destinationOf` 的四种回退，以及 `gestureLine` 的映射。`tests/files-toggle-action.client.spec.tsx` 覆盖控件的无障碍名称，以及它只执行一个手势。`tests/apply.client.spec.ts` 覆盖四项注册、`workspace-files` 这个 id、它们在 dispose 时被收回，以及该切换的三条分支：未展开、已展开且停在树上、已展开但停在别的 tab 上。
