# Agent Note: The desktop seed store merges in concurrent file batches

Status: implemented

[English](2026-10-16-desktop-seed-store-concurrent-merge.md) | 中文

## Problem

2026-10-16 的启动报告把重建路径留成了最大的一笔剩余成本。在那台机器上用一个全新的 home 与缓存好的 0.1.5-rc.25 离线包测量，一次 `--prebuild` 花费 78.7 秒：离线包校验 1.8 秒、仓库阶段 44.4 秒、profile 链接 27.3 秒、暂存运行时校验 5.1 秒、激活 0.02 秒。

仓库阶段几乎全部是 `apps/desktop/src/seed-store.ts` 里的 `copyStoreEntries`：它遍历解包出来的软件包仓库那 22 399 条条目，对每条缺失的条目做一次同步 `copyFileSync`。在全新的 home 上每条都是缺失的，于是这一趟就是 22 399 次手写串行的复制，每条约 2 毫秒。这个代价是 Windows 为每个新文件名收取的按名开销，而不是字节量：同一次测量里 profile 链接阶段为 30 110 个链接付的是每个文件约 0.9 毫秒，而 DSH NEXT 把同一个引擎放在一个打包的 `app.asar` 里、用 4.96 秒启动，而不是一棵 30 110 个文件的树。

## Decision

`copyStoreEntries` 现在按 `COOPERATIVE_BATCH_ENTRIES`（2048）条一批并发复制：对一批异步 `copyFile` 调用执行 `Promise.all`，每批上报一次进度，批与批之间把事件循环交还出去。这一趟因此与同一个文件里已有的两个模式一致：`materializeLinkedProfile` 里分批并发的链接阶段，以及 `apps/desktop/src/event-loop.ts` 里的协作式遍历契约。

逐条目的判定没有变化。`needsStoreCopy` 仍然决定某条目是否复制，所以已经存在的条目仍然不动，半途写坏的副本仍然按大小修复。同一批里的两条条目永远是两条不同的仓库相对路径，因此一批不会与自身竞争，并发度也仍然有界，而不是为仓库里每条条目各开一个句柄。

在同一台机器、同一份离线包与同样的 home 布局下测量：仓库阶段从 44.4 秒降到 34.7 秒，整个 `--prebuild` 从 78.7 秒降到 65.3 秒。

## Alternatives considered

- 保留串行复制。它是对的，而且仓库阶段不在健康启动路径上，但它是重建里最大的一块可压缩成本，而同一个文件里的链接阶段已经示范了怎么把这段延迟叠起来。
- 让离线包归档直接解包进仓库、不做暂存再复制。那样能整段省掉复制，但校验属于传输契约：分片要先通过路径、条目类型、唯一性与数量的检查，并在一个隔离目录里解包，之后任何文件才允许进入可写的软件包状态。改它属于打包决策，不属于复制循环。
- 用一次 `Promise.all` 复制全部文件。对 22 000 条条目无界并发有耗尽句柄的风险，也会饿死正在服务启动窗口的事件循环，而这正是协作式批次上界要防的事。
- 跳过暂存运行时的校验遍历，或把它并进链接阶段。那次遍历是「磁盘上的运行时完整、原生模块可加载」的独立检查；用 5.1 秒换取更小的数字，是拿一项保证去交换。
- 只给这一趟提高批次大小。这个上界与其它遍历共用，存在的理由是让 shell 保持响应，因此第二个常量需要它自己的理由。

## Consequences

启动时需要重建运行时的用户少等约 13 秒（17%）才能等到仓库与 profile 就绪；这笔收益来自把按文件的延迟叠起来，所以按名开销更慢的存储比批量吞吐更快的存储受益更明显。

这一阶段不再严格有序，因此进度分数按批推进而不是按文件推进；上报的分数被夹到 1，因为最后一批是按整批计入的。

合并期间句柄的峰值占用由批次大小决定，与 profile 链接阶段相同，而后者本来就在这个并发度上运行。

本笔记没有触碰重建的其余成本：同一阶段里的 16 分片归档解包与 SQLite `package_index` 合并、27.3 秒的链接阶段、5.1 秒的校验，以及单独的那次离线包下载，都仍然付同样的按文件价格。缩短它们、以及已安装运行时那 70 秒的冷启动首次打开，仍然是未完成的工作；这一趟所服务的仓库传输与校验规则仍由[Electron 桌面打包与更新](../architecture/2026-08-25-electron-desktop-packaging-and-updates.zh.md)拥有，这个仓库所在的 home 则由[产品 home 笔记](../bug-fix/2026-10-16-desktop-product-home-and-activation-recovery.zh.md)拥有。
